#### **2. Daily Use Cases - The Developer Experience (4 minutes)**

**Real-World Workflows:**

*Finding Service Information with Visual Qontract:*
- **Use case**: "I need to know where my service is deployed and what version is running"
- Navigate to your service in the catalog
- Visual Qontract tab shows:
  - Service pipelines (CI/CD pipeline information)
  - Clusters and namespaces where it's deployed
  - Current image tags running in each environment
  - Configuration and resource definitions
- **The win**: No more hunting through GitLab repos or OpenShift consoles - it's all in one view

*Tracking PR Status with App-Interface Plugin:*
- **Use case**: "Where is my PR in the review/merge process?"
- See review queue times - how long PRs are waiting for review
- Track merge queue times - time from approval to merge
- Visibility into bottlenecks in your development workflow
- Monitor your PR progress without constantly refreshing GitLab
- **The win**: Know exactly where your PR stands and how long it typically takes to get merged

*AI-Powered Search and Discovery with AI Projects Plugin:*
- **Use case**: "I need to find documentation, understand a concept, or discover related services"
- Convo provides intelligent, conversational search across all your documentation
- Natural language queries - ask questions like you would to a colleague
- Searches across multiple doc sources simultaneously
- Context-aware results based on your role and projects
- **The win**: Stop tabbing through multiple wikis, READMEs, and confluence pages - just ask and get intelligent answers

*Quick Access to Critical Information:*
- **Kafka-Info**: Check consumer group lag and Kafka metrics
- **Snyk**: Security vulnerabilities and dependency issues
- **Metrics & Monitoring**: Service health and performance at a glance

**The Value Proposition:**
- **One URL instead of dozens** - GitLab, OpenShift console, docs, monitoring, AI-powered search - all in one place
- **Workflow visibility** - see PR queue times and deployment status without context switching
- **Context-aware** - everything scoped to YOUR services and teams
- **AI-enhanced** - intelligent search that understands intent, not just keywords
- **Saves time** - information you need daily is one click (or one question) away

#### **3. Technical Details - Under the Hood (3.5 minutes)**

**How Plugins Are Loaded:**

*Dynamic Plugin System:*
- Plugins packaged as npm packages and stored in artifact registries
- Configuration in `dynamic-plugins.yaml` tells RHDH which plugins to load
- Init container downloads plugins at startup before main app starts
- Plugins can be frontend-only, backend-only, or full-stack

*Configuration Layers:*
- `app-config.yaml`: General Backstage configuration
- `dynamic-plugins.yaml`: Plugin-specific configuration (takes precedence)
- Environment-specific configs for dev/stage/prod

**Plugin Development:**

*We have a comprehensive plugin development guide:*
- Repository: https://gitlab.cee.redhat.com/hcm-engprod/inscope-dev/-/tree/master
- Covers the full development workflow
- Examples and best practices from our 13-plugin upgrade project

*Key Development Workflow:*
1. **Bootstrap** - Create plugin structure with modern Backstage tooling
2. **Local Development** - Test with real data using local dev environment
3. **Testing** - Local → Ephemeral → Stage → Prod
4. **Release & Deploy** - Version control and deployment pipeline

*Modern Plugin Architecture:*
- Using `@backstage/create-app` and official CLI tools
- Proper API usage (avoiding deprecated APIs)
- Testing utilities for realistic test environments
- Integration with our infrastructure (LDAP, OpenShift, internal services)

**Common Considerations:**
- **Version compatibility**: Plugins must stay in sync with RHDH version
- **Configuration precedence**: Understanding where settings come from
- **Testing strategy**: Ephemeral environments catch issues before they hit stage/prod
- **Dependencies**: Some plugins require specific backend services
